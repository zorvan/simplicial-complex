## 1. Release thesis

Version 0.4.0 established three distinct relational layers:

- simplicial complexes for downward-closed, compositional relations;
- hypergraphs for irreducible encounters;
- a context/role obstruction laboratory for locally varying readings.

The next work must first correct the topology already claimed by the interface, then introduce persistent topology as a new product capability.

| Release            | Promise                                                                                                                                         | Scope boundary                                                                                                                 |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **0.4.5**          | The topology shown by the plugin is mathematically correct and honestly named.                                                                  | Static homology, missing-face motifs, filtration validation, terminology corrections, compatibility migration. No barcode yet. |
| **0.5.0**          | The plugin reveals which topological features persist, provides inspectable cycle witnesses, and ranks writing prompts with disclosed evidence. | Persistent homology over \(\mathbb F_2\), barcode/diagram, representative cycles, uncertainty, worker execution.               |
| **0.6.0 or later** | Geometry, flow, and rigorous contextuality become separate instruments.                                                                         | Hodge decomposition, cellular-sheaf cohomology, Abramsky–Brandenburger empirical models, advanced hypergraph operators.        |

The release rule is strict: **0.5.0 does not absorb Hodge, Morse, Ricci, Mapper, diffusion maps, Rips complexes, zigzag persistence, or a rewritten contextuality model.** Those depend on the chain-complex foundation but are not required to ship persistent topology correctly.

The computational implementation ships **a sparse \(\mathbb F_2\) engine in TypeScript behind a backend interface**. The interface is designed so a Rust/WASM implementation can replace the engine without touching a caller, but Rust is **not** on the 0.4.5 or 0.5.0 critical path.

The reason is scope discipline, not preference. The 0.4.5 promise is mathematical correctness, and correct Betti numbers do not require a second toolchain. At the vault scale this plugin actually benchmarks against (500 nodes, a few thousand simplices), sparse bitset column reduction in TypeScript is a tens-of-milliseconds operation off the render loop. Sequencing a Rust toolchain, a wasm packaging decision, a CI rewrite, and an Obsidian distribution spike _ahead of_ the correctness release buys nothing the release promises and risks everything it does.

Rust/WASM becomes a ticket when — and only when — the PH-09 benchmarks show the TypeScript engine missing a stated budget on a real vault. §4.5 keeps the spike fully specified so it can be picked up unchanged at that point.

## 2. Non-negotiable mathematical standard

Every mathematical source module must begin with a comment of this form:

```ts
/**
 * Mathematical object: <domain, codomain, coefficient field, bases>.
 * Result used: <named theorem, identity, or algorithmic result>.
 * Preconditions: <finite/downward-closed/filtered/oriented/etc.>.
 * Consequence: <what the result permits this function to conclude>.
 * Witness: <what inspectable evidence the function returns>.
 * Non-claim: <important limitation or non-uniqueness>.
 * Reference: <author/title or stable bibliography key>.
 */
```

Comments must connect the theorem to the implementation. Merely writing “Hodge theory,” “sheaf obstruction,” or “persistent homology” is not sufficient.

Tests must encode the corresponding invariant. Examples:

- boundary construction: \(\partial\_{k-1}\partial_k=0\);
- static homology: Euler–Poincaré;
- persistence: every returned cycle has zero boundary;
- filtration: every face precedes or ties its coface;
- representative cycles: the stored chain contains the simplex that created the class before its death;
- contextuality terminology: local incompatibility is never labelled contextuality.

### 3.2 Incorrect or ambiguous contracts to replace

1. `core/betti.ts` counts empty triangular boundaries and tetrahedral shells. These are useful motifs, but not general β₁ and β₂. Two further defects hide inside that enumeration:
   - **The motif count itself is wrong.** `findUnfilledTriangles` (`core/betti.ts:110`) iterates every vertex `a`, then every connected neighbour pair `(b,c)`, and pushes a result each time with no deduplication. Each empty triangle is therefore emitted three times — once per vertex, so the displayed β₁ is 3× the true motif count. `findHollowTetrahedra` deduplicates through `tetraCandidates`, so β₂ is unaffected. Relocating this code without fixing it moves the bug; see MC-01.
   - **It mutates the model.** `findUnfilledTriangles` and `findHollowTetrahedra` call `.sort()` on `simplex.nodes` directly. `Array.prototype.sort` sorts in place, so these functions reorder live model arrays, using default lexicographic order while `core/normalize.ts` orders by normalized `localeCompare`. The relocated code must sort copies.
2. `Hole` conflates a missing face with a homology class.
3. `computeFiltrationEvents` detects local simplex appearances and triangle closures rather than persistence births/deaths.
4. `data/persistence.ts` means storage persistence, while encounter `persistence` means recurrence. Neither means persistent homology.
5. `core/sheaf.ts` reports `h1` as the rank of non-closing holonomy vectors without constructing a cochain complex and quotient defining \(H^1\). This must be labelled as an obstruction rank until later work establishes actual sheaf cohomology.

## 4. Target architecture

```text
SimplicialModel
    |
    +--> MissingFaceIndex ------------------> local completion prompts
    |
    +--> ChainComplex<F2>
            |
            +--> StaticHomology ------------> beta numbers + bases
            |
            +--> FilteredChainComplex
                    |
                    +--> PersistenceReducer -> intervals + pairings
                    |                              |
                    |                              +--> cycle witnesses
                    |
                    +--> BootstrapRunner -------> empirical support

TopologyAnalysisService
    +--> revision/config cache
    +--> cancellation and worker boundary
    +--> UI-safe progress and errors

PersistenceView
    +--> barcode / diagram
    +--> brush-link cycle highlight
    +--> ranked writing prompts
```

Hypergraphs remain outside `ChainComplex<F2>`. A hyperedge contributes only if the user explicitly promotes it to a simplex.

### 4.1 Backend boundary

```text
TypeScript / Obsidian
    |
    +--> validates plugin-domain invariants
    +--> creates compact typed-array snapshot
    +--> sends request to a Web Worker
              |
              +--> TypeScript sparse F2 engine
                        |
                        +--> chain complex over bitset columns
                        +--> rank and persistence reduction
                        +--> representative chains
                        +--> theorem-invariant diagnostics
```

All callers go through one interface, and that interface must not leak engine-specific types — no matrix handles, no worker message shapes, and (should Rust arrive later) no `wasm-bindgen` types:

```ts
interface TopologyBackend {
  capabilities(): TopologyCapabilities;
  computeStatic(input: TopologyInput): Promise<HomologySummary>;
  computePersistence(input: TopologyInput): Promise<PersistenceResult>;
  cancel(requestId: string): void;
}
```

For 0.4.5 and 0.5.0 there is exactly one production implementation, `TsTopologyBackend`, plus a naive checker used only in tests:

- `TsTopologyBackend`: sparse \(\mathbb F_2\) columns as `Uint32Array` bitsets, running in a worker. The shipped engine.
- `NaiveTopologyChecker`: a deliberately slow, obviously-correct dense implementation over tiny fixtures. It exists so the optimized sparse path has an independent oracle, and it must never be reachable from production code paths.

A `WasmTopologyBackend` is the intended third implementation if §4.5 is ever triggered. Writing the interface now is the whole point; writing the Rust now is not.

**Why an interface at all, given one implementation:** it keeps the worker boundary, cancellation semantics, and serializable result shapes honest from the first ticket, so the later engine swap is a file addition rather than a refactor of every caller.

### 4.2 Dependency policy

The 0.4.5/0.5.0 default is **no new runtime dependency**. The algebra required — sparse XOR, pivot lookup, rank, kernel basis, filtered column reduction — is a few hundred lines and is exactly the code whose correctness the release is selling. Vendoring it means the theorem comments in §2 describe code this repository can test.

If a dependency is nonetheless proposed (now, or for the deferred Rust engine), record:

- license compatibility and transitive licenses;
- maintenance and release history;
- WASM support without filesystem, threads, or unsupported native dependencies;
- deterministic behavior and coefficient-field support;
- ability to accept an arbitrary filtered simplicial complex, not only a Vietoris–Rips distance matrix;
- representative-cycle support;
- peak memory and bundle-size cost;
- whether the implementation exposes enough provenance to verify theorem invariants.

For the deferred Rust engine: use an existing crate when it satisfies the contract, wrap or fork an upstream algorithm when it is mathematically suitable but lacks a stable WASM API, and implement only the missing substrate locally. Ripser is reserved for later Vietoris–Rips work: its standard engine is optimized for Rips filtrations and does not provide the representative-cycle contract required for 0.5.0.

### 4.3 Worker packaging — required in 0.5.0

Independent of any Rust question, moving computation off the main thread has a packaging cost this repository has not paid yet, and PH-04 depends on it.

Obsidian's community-plugin installer downloads only the assets named in the release: `manifest.json`, `main.js`, `styles.css`. A sibling `workers/topology.js` file is not fetched and will not exist in an installed vault. `build.mjs` compounds this: it produces a single CJS `main.js` and then runs Prettier over that file until the formatting stabilizes, and `main.js` is a committed artifact.

Therefore `WORKER-00`, a small ticket ahead of PH-04:

1. Bundle the worker entry as a separate esbuild pass into an inlined string, and start it from a `Blob` URL created at runtime. Do not add a second emitted file.
2. Verify the blob worker starts under Obsidian desktop (Electron) and Obsidian mobile. `manifest.json` currently declares `"isDesktopOnly": false`, so mobile is in scope until a deliberate decision says otherwise — see §4.4.
3. Verify plugin enable, disable, reload, update, vault switch, and worker termination leave no orphaned worker.
4. Confirm `main.js` size growth and that `prettifyBundle` still converges within its pass limit with the inlined worker string present.
5. Add a `scripts/verify.mjs` preflight assertion that the built `main.js` contains the worker payload.

**Exit criterion:** a clean installed-plugin test runs a topology computation in a worker on every supported platform, with no network access and no extra files in the plugin folder.

### 4.4 Mobile support — decide before PH-04, not during it

`manifest.json` sets `"isDesktopOnly": false` today. Flipping it to `true` is a user-visible regression that removes the plugin from existing mobile installations, so it is a product decision and must be recorded before worker and topology work begins, with one of two outcomes:

- **Mobile stays supported:** PH-04 budgets, `WORKER-00`, and the visual fixtures all include mobile, and the memory limits in PH-04.5 are set from the mobile ceiling rather than the desktop one.
- **Mobile is dropped:** `manifest.json`, `README.md`, and the changelog say so explicitly in the same release, and the deprecation is announced rather than discovered.

### 4.5 Deferred: Rust/WASM engine (`WASM-00`)

**Trigger:** a PH-09 benchmark shows `TsTopologyBackend` missing a stated budget on a representative vault. Not before.

Kept fully specified so it can be executed unchanged when triggered:

1. Create `crates/topology-engine/` with a minimal `wasm-bindgen` export that accepts typed arrays and returns a deterministic checksum/result.
2. Build with pinned Rust, `wasm-bindgen`, and `wasm-pack` versions. Test `--target web` and direct `WebAssembly.instantiate`; do not assume esbuild handles wasm-bindgen's default bundler target correctly.
3. Load the module from the existing blob worker in an installed Obsidian plugin — not only from the development server or Node tests.
4. Verify every platform still in scope per §4.4.
5. Verify production artifacts contain everything Obsidian installs. Do not depend on Rust, npm, a compiler, network access, or a sidecar executable at runtime.
6. Test plugin enable, disable, reload, update, vault switch, worker termination, and a path containing spaces/non-ASCII characters.
7. Measure compressed/uncompressed bundle size, initialization latency, one warm call, and memory release after worker termination.
8. Add a release-preflight assertion that the embedded wasm bytes exist and their checksum matches the generated JavaScript binding.

**Deployment constraint, not a choice:** because the installer fetches only the three named assets, the wasm bytes must be embedded in `main.js` (base64, ~1.37× the binary size). A separately emitted `.wasm` file is not a supported option for community-plugin distribution. The spike must therefore measure the effect on the committed `main.js`: current size is ~316 KB, Prettier reformats the whole file on every build, and the artifact is in version control. If embedding pushes that past what is reasonable to commit and re-format, the spike's output is a build-pipeline change proposal (stop committing `main.js`, or exclude the payload from `prettifyBundle`) — not an improvised release-week workaround.

**CI cost, to be scoped inside the spike:** `.github/workflows/ci.yml` is four Node-only jobs, and `scripts/verify.mjs` is documented as mirroring it step for step. Rust means a pinned toolchain plus `wasm-pack` in both, and a `CONTRIBUTING.md` rewrite so a contributor with only Node can still build and test the plugin. Budget this as part of the spike, not as follow-up.

**Spike exit criterion:** a clean installed-plugin test loads and runs the same wasm build in the main supported Obsidian environments, with no network access and no developer toolchain installed, _and_ the measured speedup justifies the second toolchain. If either fails, keep `TsTopologyBackend` and close the spike.

### 5.1 Ticket MC-01 — split missing-face motifs from homology

**Files:** `core/types.ts`, new `core/missing-faces.ts`, `core/betti.ts`, `data/explainer.ts`, `data/inference/rules/open-triad.ts`, `render/components/holes.ts`, `render/renderer.ts`, `ui/panel.ts`

**Work:**

1. Introduce:

   ```ts
   interface MissingFaceBoundary {
     dimension: 1 | 2;
     boundaryNodes: NodeID[];
     missingSimplex: NodeID[];
   }
   ```

2. Move empty-triangle and tetrahedral-shell enumeration from `core/betti.ts` into `core/missing-faces.ts`. **Move it corrected, not verbatim** — see steps 6 and 7.
3. Rename UI language:
   - “hole” → “missing face” or “completion opportunity” for these motifs;
   - “fills β₁ hole” → “fills a triangular missing face”;
   - “β₂ void” → “tetrahedral boundary missing its 3-simplex.”
4. Delete `Hole` rather than aliasing it. No compatibility path is owed: `package.json` is `"private": true`, the plugin exports no public API, and Betti results are never serialized — `data/persistence.ts` writes notes and settings, and `core/model.ts` holds Betti only in an in-memory analysis cache. §8 is amended to match.

**Theory comment:** explain that a missing \((k+1)\)-simplex boundary is a cycle, but it need not form an independent homology class; it may already be a boundary of another chain.

**Tests:**

- triangular boundary is **exactly one** missing-face motif, not three (regression test for the deduplication fix);
- a complex of _n_ empty triangles yields _n_ motifs, independent of vertex iteration order;

- square boundary has no missing triangular face;

**Done when:** no code path derives a Betti number by counting `MissingFaceBoundary` values.

### 5.2 Ticket MC-02 — canonical chain-complex engine over \(\mathbb F_2\)

**Files:** new `core/topology/backend.ts`, new `core/topology/chain-complex.ts`, new `core/topology/ts-backend.ts`, new `core/topology/naive-checker.ts` (test-only), `core/model.ts`, `core/types.ts`

**Data structures:**

```ts
type SparseColumn = Uint32Array; // sorted row indices with coefficient 1

interface ChainBasis {
  dimension: number;
  simplices: SimplexKey[];
  index: Map<SimplexKey, number>;
}

interface BoundaryOperator {
  dimension: number;
  rows: ChainBasis;
  columns: ChainBasis;
  data: SparseColumn[];
}

interface ChainComplex {
  bases: ChainBasis[];
  boundaries: BoundaryOperator[];
  maxDimension: number;
}
```

**Work:**

1. Define the wire format using flat typed arrays: simplex offsets, vertex indices, dimensions, filtration values, and stable-key indices. Avoid per-simplex JSON across the worker boundary. Design it as a _serialization_ format, not as an in-process object graph, so the worker move in PH-04 and any later engine swap need no change here.
2. Revalidate the input inside the engine. Caller-side validation protects the user; engine-side validation protects the mathematical invariants at the trust boundary and keeps the engine independently testable.
3. Define canonical simplex order by dimension, then normalized vertex IDs.
4. Construct each boundary column from codimension-one faces.
5. Over \(\mathbb F_2\), omit orientation signs because \(-1=1\).
6. Reject or diagnose a model that is not downward closed; do not silently manufacture faces inside the analyzer.
7. Represent columns as `Uint32Array` bitsets and implement sparse XOR, pivot (`low`) lookup, rank, and kernel-basis extraction directly. Do not route binary algebra through dense matrices or through generic numeric arrays.
8. Keep this engine separate from `core/linalg.ts`, whose rational `Fraction` matrices serve different mathematics and stay reserved for the sheaf layer.
9. Return owned typed arrays and structured-cloneable results; retain no callbacks and no references to caller state beyond a call.
10. Add conformance fixtures asserting `TsTopologyBackend` and `NaiveTopologyChecker` agree on every fixture in §7.1.

**Theory comment:** chain groups \(C_k(K;\mathbb F_2)\), simplicial boundary, boundary-of-boundary theorem.

**Tests:**

- canonical basis is deterministic under insertion-order changes;
- every boundary row references a face in the previous basis;
- \(\partial\_{k-1}\partial_k=0\) for every fixture;
- empty and zero-dimensional complexes behave correctly;
- tetrahedron boundary columns are correct.

**Done when:** chain construction is deterministic, sparse, independently reproduced by `NaiveTopologyChecker`, and within the MC-00 budget at every measured vault size.

### 5.3 Ticket MC-03 — compute actual Betti numbers

**Files:** replace `core/betti.ts`, update `core/types.ts`, `core/model.ts`, `render/components/hud.ts`, `tests/core.test.ts`, `tests/hypergraph.test.ts`

**Formula:**

\[
\beta*k=\dim C_k-\operatorname{rank}\partial_k-\operatorname{rank}\partial*{k+1}.
\]

This follows from rank-nullity and \(H*k=\ker\partial_k/\operatorname{im}\partial*{k+1}\).

**Work:**

1. Return β₀ through the same boundary-rank pipeline used for higher dimensions.
2. Preserve the existing `{b0,b1,b2}` surface where practical, but remove `holes` from `BettiResult`.
3. Optionally include ranks and simplex counts as provenance:

   ```ts
   interface HomologySummary {
     coefficientField: "F2";
     betti: number[];
     chainDimensions: number[];
     boundaryRanks: number[];
     /** Top dimension actually analyzed. Invariants below hold for this skeleton only. */
     maxDimension: number;
     modelRevision: number;
   }
   ```

4. Update caching and invalidation in `core/model.ts` (`getCachedBetti`, `getAnalysisSummary`, `computeAnalysisSummary`), and drop `holeCount` from `AnalysisSummary` in favour of a separately named missing-face count.
5. Ensure hyperedge mutations do not invalidate or perturb simplicial homology unless they also change a simplex.
6. **Decide the fate of `enableBettiComputation`.** The setting is labelled “Compute holes (slow)” (`ui/view.ts:397`) and gates HUD display and hole hit-testing in five places in `render/renderer.ts`. After this ticket the label is wrong twice over: the results are not holes, and boundary-rank computation is expected to be _cheaper_ than the current O(n·d²) triad walk. Confirm against MC-00 numbers, then either retire the toggle (preferred, if the measurement supports it) or relabel it as a display toggle rather than a computation toggle. Preserving the settings key is fine; preserving the claim is not.
7. **Bound the analyzed dimension explicitly.** The model admits simplices of any size and `core/faces.ts` generates all faces, so β₃ and above can be nonzero in a real vault. Record the top dimension analyzed in `HomologySummary` and state in the UI that invariants are reported for the analyzed skeleton.

**Truth fixtures:**

| Fixture                  | Expected Betti numbers |
| ------------------------ | ---------------------- |
| Empty complex            | all zero               |
| Three isolated vertices  | (3, 0, 0)              |
| Tree                     | (1, 0, 0)              |
| Square boundary          | (1, 1, 0)              |
| Filled triangulated disk | (1, 0, 0)              |
| Wedge of two circles     | (1, 2, 0)              |
| Boundary of tetrahedron  | (1, 0, 1)              |
| Filled tetrahedron       | (1, 0, 0)              |
| Two disconnected circles | (2, 2, 0)              |

**Invariant test:**

\[
\sum_k(-1)^k f_k=\sum_k(-1)^k\beta_k.
\]

**This identity must be stated over the skeleton actually analyzed.** It holds when the sums run over the same range of \(k\). If the complex contains simplices above the analyzed dimension \(d\) — which a vault can, since simplices carry any number of nodes and `core/faces.ts` generates their faces — then \(\sum*k(-1)^kf_k\) over \_all* \(k\) is compared against a \(\beta\) vector that was never computed above \(d\), and the test fails on correct code.

Accordingly:

- compute \(f_k\) and \(\beta_k\) over the same truncation, i.e. the \(d\)-skeleton;
- when a fixture contains simplices above \(d\), assert the identity for the truncated complex and record the truncation in the failure message;
- the §7.2 property-test generator must either bound generated dimension to \(d\) or compute \(\beta\) up to each fixture's top dimension.

Stating it any other way turns a real gate into an intermittent false alarm, and a gate people learn to ignore is worse than no gate.

**Done when:** all truth fixtures and the truncation-aware Euler–Poincaré test pass, and the HUD displays actual Betti numbers.

3. Return diagnostics when raw weights are repaired to satisfy the face condition.
4. Support maximum homology dimension 2 initially; include \((k+1)\)-simplices needed to kill \(H_k\).

**Done when:** every ordered prefix is a simplicial complex.

### 6.2 Ticket PH-02 — persistence reduction over \(\mathbb F_2\)

**Files:** new `core/topology/persistence.ts`, new `core/topology/persistence-types.ts`, `core/topology/ts-backend.ts`

**Algorithm:** standard left-to-right filtered boundary-column reduction.

```ts
interface PersistenceInterval {
  dimension: number;
  birth: number;
  death: number | null;
  birthSimplex: SimplexKey;
  deathSimplex?: SimplexKey;
  lifetime: number | null;
}
```

**Work:**

1. Reduce each sparse column until its lowest row is unique or the column becomes zero.
2. Pair the pivot row's simplex with the current simplex.
3. Emit essential intervals for unpaired births.
4. Keep zero-length intervals internally for verification; hide them by default in the UI.
5. Never call this Smith normal form. The filtration order is essential and must be preserved.
6. Add cooperative cancellation checks between reduction batches, so a long reduction yields to a cancellation message without the worker being destroyed. Worker termination remains the hard-cancel fallback; see PH-04.7 for its cost.
7. Add deterministic output and explicit memory accounting.
8. Implement locally per §4.2 rather than adopting a dependency. Keep the wire contract and the conformance suite stable so a later engine swap (§4.5) changes no caller and no test.

**Theory comments:** persistence module induced by the filtered complex; interval decomposition for finite one-parameter persistence; matrix-reduction pairing theorem.

**Tests:**

- known barcode fixtures;
- static β at threshold equals intervals alive at that threshold;
- insertion-order invariance for tie-free input;
- deterministic tie behavior;
- essential intervals survive to `death: null`;
- empty, disconnected, and filled fixtures.

**Done when:** reduction is the sole source of topological birth/death events.

### 6.7 Ticket PH-07 — empirical uncertainty

**Files:** new `core/topology/bootstrap.ts`, worker integration, settings, tests

**Initial sampling contract:** stratified subsampling of notes/encounters, preserving configured folder/time strata. Weight perturbation is a separate mode and must not share labels with subsampling.

**Default: off.** Bootstrap multiplies a full reduction plus a diagram matching by the resample count. It is an opt-in analysis with a visible cost, not a background behaviour, and it ships disabled with an explicit computation budget attached to the setting.

**Work:**

1. Use deterministic seeded runs.
2. Rebuild the induced simplicial complex and diagram for each resample.
3. Match resampled features to the full diagram using bottleneck matching initially.
4. Report:
   - support frequency;
   - birth/death quantiles;
   - unmatched rate;
   - sample count and seed;
   - exact sampling scheme.
5. Call these “empirical stability” or “bootstrap support,” not formal confidence bands unless coverage is later established.
6. Run only on demand or during idle time; permit cancellation and a computation budget.

**Theory comment:** bottleneck stability bounds diagram perturbation when filtered functions are close in the appropriate norm. Bootstrap support is an empirical procedure and is not supplied by the stability theorem.

**Done when:** a seeded fixture with an injected robust loop ranks above short-lived resampling artifacts.

## 7. Testing strategy

### 7.1 Deterministic fixtures

Create `fixtures/topology/` with machine-readable complexes and expected results:

- `tree`;
- `square-cycle`;
- `wedge-two-circles`;
- `triangulated-disk`;
- `annulus`;
- `tetrahedron-boundary`;
- `filled-tetrahedron`;
- `two-components`;
- `weighted-cycle-born-and-filled`;
- `equal-weight-face-coface`;
- `hyperedge-only-encounter`.

Each fixture should declare expected static Betti numbers, filtration order, intervals, and representative validation—not necessarily an exact representative when several bases are valid.

### 7.2 Property tests

Generate bounded small downward-closed complexes and check:

1. \(\partial^2=0\).
2. Euler–Poincaré, over the analyzed skeleton — either bound the generator to the analyzed dimension or compute β to each generated complex's top dimension (MC-03).
3. Betti numbers are non-negative integers.
4. Relabelling vertices preserves Betti numbers and interval multisets.
5. Every persistence representative is a cycle.
6. Static Betti at each distinct filtration value equals the alive interval count.
7. Adding hyperedges alone leaves all simplicial invariants unchanged.

Use deterministic seeds and print the failing seed.

### 7.3 Regression tests

Keep current hypergraph, activation, persistence-storage, and sheaf tests. Add explicit tests preventing terminology regression:

- no missing-face explainer emits “β₁”;
- no current holonomy report emits “H¹” before actual cohomology exists;
- no storage-persistence type is accepted where a persistence interval is required.

### 7.4 Visual tests

Add deterministic SVG fixtures for:

- missing face versus representative cycle;
- finite versus essential bar;
- selected/hovered barcode link;
- light/dark themes;
- reduced motion;
- uncertainty support display;
- limited-computation and stale-result states.

## 8. Migration and compatibility

1. Avoid changes to note syntax in 0.4.5 and 0.5.0.
2. Do not serialize Betti numbers, barcodes, or representatives; derive and cache them.
3. Maintain existing settings defaults, adding new settings through merged defaults. The one deliberate exception is `enableBettiComputation`, whose disposition MC-03.6 decides.
4. Remove `Hole` outright in 0.4.5. Nothing external depends on it: the package is private, no plugin API is exported, and Betti results live only in the in-memory analysis cache. A deprecation alias here would preserve a name whose meaning the release exists to correct.
5. Preserve encounter `persistence` in stored data but label it “recurrence” in new UI copy. A future schema migration may rename the field.
6. Do not mutate existing sheaf/context data during the terminology correction.
7. Increment cache schema versions whenever filtration order or pairing logic changes.

## 12. Definition of success

Version 0.4.5 succeeds when the plugin stops confusing conspicuous missing faces with homology.
