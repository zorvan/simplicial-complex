# Simplicial Complex Plugin — v0.4.5 and v0.5.0 Implementation Plan

**Status:** Proposed  
**Prepared:** 2026-08-03  
**Starting point:** v0.4.0  
**Source audit:** [`Reframe-stop-computing-numbers-start-revealing-shape.md`](./Reframe-stop-computing-numbers-start-revealing-shape.md)

## 1. Release thesis

Version 0.4.0 established three distinct relational layers:

- simplicial complexes for downward-closed, compositional relations;
- hypergraphs for irreducible encounters;
- a context/role obstruction laboratory for locally varying readings.

The next work must first correct the topology already claimed by the interface, then introduce persistent topology as a new product capability.

| Release            | Promise                                                                                                                                         | Scope boundary                                                                                                                 |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **0.4.5**          | The topology shown by the plugin is mathematically correct and honestly named.                                                                  | Static homology, missing-face motifs, filtration validation, terminology corrections, compatibility migration. No barcode yet. |
| **0.5.0**          | The plugin reveals which topological features persist, provides inspectable cycle witnesses, and ranks writing prompts with disclosed evidence. | Persistent homology over \(\mathbb F_2\), barcode/diagram, representative cycles, uncertainty, worker execution.               |
| **0.6.0 or later** | Geometry, flow, and rigorous contextuality become separate instruments.                                                                         | Hodge decomposition, cellular-sheaf cohomology, Abramsky–Brandenburger empirical models, advanced hypergraph operators.        |

The release rule is strict: **0.5.0 does not absorb Hodge, Morse, Ricci, Mapper, diffusion maps, Rips complexes, zigzag persistence, or a rewritten contextuality model.** Those depend on the chain-complex foundation but are not required to ship persistent topology correctly.

The computational implementation will use a **Rust/WASM engine behind a TypeScript contract**. Rust owns sparse boundary algebra, homology, persistence reduction, and representative chains. TypeScript owns Obsidian integration, model extraction, filtration provenance, UI, caching policy, and user-facing mathematical explanations.

## 2. Non-negotiable mathematical standard

Every mathematical source module must begin with a comment of this form:

```ts
/**
 * Mathematical object: <domain, codomain, coefficient field, bases>.
 * Result used: <named theorem, identity, or algorithmic result>.
 * Preconditions: <finite/downward-closed/filtered/oriented/etc.>.
 * Consequence: <what the result permits this function to conclude>.
 * Witness: <what inspectable evidence the function returns>.
 * Non-claim: <important limitation or non-uniqueness>.
 * Reference: <author/title or stable bibliography key>.
 */
```

Comments must connect the theorem to the implementation. Merely writing “Hodge theory,” “sheaf obstruction,” or “persistent homology” is not sufficient.

Tests must encode the corresponding invariant. Examples:

- boundary construction: \(\partial\_{k-1}\partial_k=0\);
- static homology: Euler–Poincaré;
- persistence: every returned cycle has zero boundary;
- filtration: every face precedes or ties its coface;
- representative cycles: the stored chain contains the simplex that created the class before its death;
- contextuality terminology: local incompatibility is never labelled contextuality.

### 3.2 Incorrect or ambiguous contracts to replace

1. `core/betti.ts` counts empty triangular boundaries and tetrahedral shells. These are useful motifs, but not general β₁ and β₂.
2. `Hole` conflates a missing face with a homology class.
3. `computeFiltrationEvents` detects local simplex appearances and triangle closures rather than persistence births/deaths.
4. `data/persistence.ts` means storage persistence, while encounter `persistence` means recurrence. Neither means persistent homology.
5. `core/sheaf.ts` reports `h1` as the rank of non-closing holonomy vectors without constructing a cochain complex and quotient defining \(H^1\). This must be labelled as an obstruction rank until later work establishes actual sheaf cohomology.

## 4. Target architecture

```text
SimplicialModel
    |
    +--> MissingFaceIndex ------------------> local completion prompts
    |
    +--> ChainComplex<F2>
            |
            +--> StaticHomology ------------> beta numbers + bases
            |
            +--> FilteredChainComplex
                    |
                    +--> PersistenceReducer -> intervals + pairings
                    |                              |
                    |                              +--> cycle witnesses
                    |
                    +--> BootstrapRunner -------> empirical support

TopologyAnalysisService
    +--> revision/config cache
    +--> cancellation and worker boundary
    +--> UI-safe progress and errors

PersistenceView
    +--> barcode / diagram
    +--> brush-link cycle highlight
    +--> ranked writing prompts
```

Hypergraphs remain outside `ChainComplex<F2>`. A hyperedge contributes only if the user explicitly promotes it to a simplex.

### 4.1 Language and dependency boundary

```text
TypeScript / Obsidian
    |
    +--> validates plugin-domain invariants
    +--> creates compact typed-array snapshot
    +--> sends request to Web Worker
              |
              +--> loads bundled topology_engine.wasm
                        |
                        +--> Rust chain complex
                        +--> F2 rank and persistence reduction
                        +--> representative chains
                        +--> theorem-invariant diagnostics
```

The public TypeScript interface must not expose `wasm-bindgen`, Rust allocation handles, or library-specific types:

```ts
interface TopologyBackend {
  capabilities(): TopologyCapabilities;
  computeStatic(input: TopologyInput): Promise<HomologySummary>;
  computePersistence(input: TopologyInput): Promise<PersistenceResult>;
  cancel(requestId: string): void;
}
```

Provide two implementations:

- `WasmTopologyBackend`: production backend;
- `ReferenceTopologyBackend`: deliberately small TypeScript implementation used for tiny fixtures, cross-backend verification, and a graceful diagnostic fallback.

The reference backend is not a second production-scale engine. Its purpose is to make Rust/WASM results independently testable and to prevent a toolchain failure from making mathematical correctness opaque.

### 4.2 Dependency policy

Before adopting a Rust crate or npm package, record:

- license compatibility and transitive licenses;
- maintenance and release history;
- WASM support without filesystem, threads, or unsupported native dependencies;
- deterministic behavior and coefficient-field support;
- ability to accept an arbitrary filtered simplicial complex, not only a Vietoris–Rips distance matrix;
- representative-cycle support;
- peak memory and bundle-size cost;
- whether the implementation exposes enough provenance to verify theorem invariants.

Use an existing crate when it satisfies the contract. Wrap or fork an upstream algorithm when it is mathematically suitable but lacks a stable WASM API. Implement only the missing substrate locally. Ripser is reserved for later Vietoris–Rips work: its standard engine is optimized for Rips filtrations and does not provide the representative-cycle contract required for 0.5.0.

### 4.3 Deployment spike — must precede topology implementation

Add a time-boxed `WASM-00` spike before `MC-02`:

1. Create `crates/topology-engine/` with a minimal `wasm-bindgen` export that accepts typed arrays and returns a deterministic checksum/result.
2. Build with pinned Rust, `wasm-bindgen`, and `wasm-pack` versions. Test `--target web` and direct `WebAssembly.instantiate`; do not assume esbuild handles wasm-bindgen's default bundler target correctly.
3. Load the module from a dedicated worker in an installed Obsidian plugin—not only from the development server or Node tests.
4. Verify desktop platforms and Obsidian mobile if mobile remains supported. A desktop-only decision must be explicit in `manifest.json` and documentation.
5. Verify production artifacts contain everything Obsidian installs. Do not depend on Rust, npm, a compiler, network access, or a sidecar executable at runtime.
6. Test plugin enable, disable, reload, update, vault switch, worker termination, and a path containing spaces/non-ASCII characters.
7. Measure compressed/uncompressed bundle size, initialization latency, one warm call, and memory release after worker termination.
8. Add a release-preflight assertion that the expected wasm bytes or embedded asset exist and their checksum matches the generated JavaScript binding.

**Deployment decision:** prefer embedding the wasm bytes into the generated plugin bundle if the size remains acceptable. This avoids reliance on extra plugin files and path resolution. If emitted as a separate asset, the release workflow and installation test must prove that Obsidian packages and resolves it on every supported platform.

**Spike exit criterion:** a clean installed-plugin test loads and runs the same wasm build in the main supported Obsidian environments, with no network access and no developer toolchain installed. If this fails, keep the TypeScript backend for 0.4.5 and defer Rust/WASM rather than improvising deployment during 0.5.0 release work.

   ```ts
   interface MissingFaceBoundary {

   }
   ```

2. Move empty-triangle and tetrahedral-shell enumeration from `core/betti.ts` into `core/missing-faces.ts`.
3. Rename UI language:
   - “hole” → “missing face” or “completion opportunity” for these motifs;
   - “fills β₁ hole” → “fills a triangular missing face”;

4. Keep a deprecated `Hole` alias for one release only if stored/plugin API compatibility requires it.

### 5.2 Ticket MC-02 — Rust canonical chain-complex engine over \(\mathbb F_2\)

**Files:** new `crates/topology-engine/`, new `core/topology/backend.ts`, new `core/topology/wasm-backend.ts`, new `core/topology/reference-backend.ts`, `core/model.ts`, `core/types.ts`, `build.mjs`

**Data structures:**

```ts
type SparseColumn = Uint32Array; // sorted row indices with coefficient 1

interface ChainBasis {
  dimension: number;
  simplices: SimplexKey[];
  index: Map<SimplexKey, number>;
}

interface BoundaryOperator {
  dimension: number;
  rows: ChainBasis;
  columns: ChainBasis;
  data: SparseColumn[];
}

interface ChainComplex {
  bases: ChainBasis[];
  boundaries: BoundaryOperator[];
  maxDimension: number;
}
```

**Work:**

1. Define the wire format in TypeScript using flat typed arrays: simplex offsets, vertex indices, dimensions, filtration values, and stable-key indices. Avoid per-simplex JSON across the worker/WASM boundary.
2. Revalidate the input in Rust. TypeScript validation protects the user; Rust validation protects memory safety and mathematical invariants at the trust boundary.
3. Define canonical simplex order by dimension, then normalized vertex IDs.
4. Construct each boundary column from codimension-one faces.
5. Over \(\mathbb F_2\), omit orientation signs because \(-1=1\).
6. Reject or diagnose a model that is not downward closed; do not silently manufacture faces inside the analyzer.
7. Use or implement sparse XOR, pivot lookup, rank, and kernel-basis extraction in Rust. Do not route binary sparse algebra through dense JavaScript matrices.
8. Keep the Rust engine separate from `core/linalg.ts`, whose rational `Fraction` matrices serve different mathematics.
9. Return owned typed arrays/serializable results; do not retain JavaScript callbacks or expose Rust pointers beyond a call.
10. Add `cargo test`, wasm integration tests, and TypeScript/Rust conformance fixtures.

**Theory comment:** chain groups \(C_k(K;\mathbb F_2)\), simplicial boundary, boundary-of-boundary theorem.

**Tests:**

- canonical basis is deterministic under insertion-order changes;
- every boundary row references a face in the previous basis;
- \(\partial\_{k-1}\partial_k=0\) for every fixture;
- empty and zero-dimensional complexes behave correctly;
- tetrahedron boundary columns are correct.

**Done when:** chain construction is deterministic, sparse, independently reproduced by the tiny TypeScript reference backend, and usable from an installed Obsidian build without a runtime toolchain.

### 5.3 Ticket MC-03 — compute actual Betti numbers

**Files:** replace `core/betti.ts`, update `core/types.ts`, `core/model.ts`, `render/components/hud.ts`, `tests/core.test.ts`, `tests/hypergraph.test.ts`

**Formula:**

\[
\beta*k=\dim C_k-\operatorname{rank}\partial_k-\operatorname{rank}\partial*{k+1}.
\]

This follows from rank-nullity and \(H*k=\ker\partial_k/\operatorname{im}\partial*{k+1}\).

**Work:**

1. Return β₀ through the same boundary-rank pipeline used for higher dimensions.
2. Preserve the existing `{b0,b1,b2}` surface where practical, but remove `holes` from `BettiResult`.
3. Optionally include ranks and simplex counts as provenance:

   ```ts
   interface HomologySummary {
     coefficientField: "F2";
     betti: number[];
     chainDimensions: number[];
     boundaryRanks: number[];
     modelRevision: number;
   }
   ```

4. Update caching and invalidation in `core/model.ts`.
5. Ensure hyperedge mutations do not invalidate or perturb simplicial homology unless they also change a simplex.

**Truth fixtures:**

| Fixture                  | Expected Betti numbers |
| ------------------------ | ---------------------- |
| Empty complex            | all zero               |
| Three isolated vertices  | (3, 0, 0)              |
| Tree                     | (1, 0, 0)              |
| Square boundary          | (1, 1, 0)              |
| Filled triangulated disk | (1, 0, 0)              |
| Wedge of two circles     | (1, 2, 0)              |
| Boundary of tetrahedron  | (1, 0, 1)              |
| Filled tetrahedron       | (1, 0, 0)              |
| Two disconnected circles | (2, 2, 0)              |

**Invariant test:**

\[
\sum_k(-1)^k f_k=\sum_k(-1)^k\beta_k.
\]

**Done when:** all truth fixtures and Euler–Poincaré pass, and the HUD displays actual Betti numbers.

### 6.2 Ticket PH-02 — Rust persistence reduction over \(\mathbb F_2\)

**Files:** Rust modules under `crates/topology-engine/src/`, new `core/topology/persistence-types.ts`, `core/topology/wasm-backend.ts`

**Algorithm:** standard left-to-right filtered boundary-column reduction.

```ts
interface PersistenceInterval {
  dimension: number;
  birth: number;
  death: number | null;
  birthSimplex: SimplexKey;
  deathSimplex?: SimplexKey;
  lifetime: number | null;
}
```

**Work:**

1. Reduce each sparse column until its lowest row is unique or the column becomes zero.
2. Pair the pivot row's simplex with the current simplex.
3. Emit essential intervals for unpaired births.
4. Keep zero-length intervals internally for verification; hide them by default in the UI.
5. Never call this Smith normal form. The filtration order is essential and must be preserved.
6. Add cooperative cancellation checks between reduction batches. Since a running synchronous wasm export cannot process a JavaScript cancellation callback reliably, partition work or terminate the dedicated worker as the hard-cancel fallback.
7. Add deterministic output and explicit memory accounting.
8. Evaluate suitable Rust crates against the dependency policy; do not select one solely because its README says “persistent homology.” Keep the wire contract and conformance suite stable if the internal crate changes.

**Theory comments:** persistence module induced by the filtered complex; interval decomposition for finite one-parameter persistence; matrix-reduction pairing theorem.

**Tests:**

- known barcode fixtures;
- static β at threshold equals intervals alive at that threshold;
- insertion-order invariance for tie-free input;
- deterministic tie behavior;
- essential intervals survive to `death: null`;
- empty, disconnected, and filled fixtures.

**Done when:** reduction is the sole source of topological birth/death events.

## 7. Testing strategy

### 7.1 Deterministic fixtures

Create `fixtures/topology/` with machine-readable complexes and expected results:

- `tree`;
- `square-cycle`;
- `wedge-two-circles`;
- `triangulated-disk`;
- `annulus`;
- `tetrahedron-boundary`;
- `filled-tetrahedron`;
- `two-components`;
- `weighted-cycle-born-and-filled`;
- `equal-weight-face-coface`;
- `hyperedge-only-encounter`.

Each fixture should declare expected static Betti numbers, filtration order, intervals, and representative validation—not necessarily an exact representative when several bases are valid.

### 7.2 Property tests

Generate bounded small downward-closed complexes and check:

1. \(\partial^2=0\).
2. Euler–Poincaré.
3. Betti numbers are non-negative integers.
4. Relabelling vertices preserves Betti numbers and interval multisets.
5. Every persistence representative is a cycle.
6. Static Betti at each distinct filtration value equals the alive interval count.
7. Adding hyperedges alone leaves all simplicial invariants unchanged.

Use deterministic seeds and print the failing seed.

### 7.3 Regression tests

Keep current hypergraph, activation, persistence-storage, and sheaf tests. Add explicit tests preventing terminology regression:

- no missing-face explainer emits “β₁”;
- no current holonomy report emits “H¹” before actual cohomology exists;
- no storage-persistence type is accepted where a persistence interval is required.

### 7.4 Visual tests

Add deterministic SVG fixtures for:

- missing face versus representative cycle;
- finite versus essential bar;
- selected/hovered barcode link;
- light/dark themes;
- reduced motion;
- uncertainty support display;
- limited-computation and stale-result states.

## 8. Migration and compatibility

1. Avoid changes to note syntax in 0.4.5 and 0.5.0.
2. Do not serialize Betti numbers, barcodes, or representatives; derive and cache them.
3. Maintain existing settings defaults, adding new settings through merged defaults.
4. If `Hole` is exported, retain a deprecated alias through 0.4.5 and remove it in 0.5.0 after internal callers migrate.
5. Preserve encounter `persistence` in stored data but label it “recurrence” in new UI copy. A future schema migration may rename the field.
6. Do not mutate existing sheaf/context data during the terminology correction.
7. Increment cache schema versions whenever filtration order or pairing logic changes.

## 12. Definition of success

Version 0.4.5 succeeds when the plugin stops confusing conspicuous missing faces with homology.

Version 0.5.0 succeeds when a user can ask:

> Which conceptual gaps persist across reasonable thresholds, what notes form one concrete witness, how stable is the observation, and why did the plugin rank it?
